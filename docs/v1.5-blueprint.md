## 1. Pipeline (updated)

``` text
Detect → Normalize → Discover → Index → Score → Plan → Enhance → Return
    │                    │          │        │        │
    ▼                    ▼          ▼        ▼        ▼
 pass-through     4 sources    fingerprint  confidence  multi-step
 (safe)           (locked)     incremental  bands       plan + fallbacks
```

Changes vs. v1:
- **Normalize** is now an explicit stage (synonyms, cross-language aliases, stemming-lite) — it feeds both scoring and compound-intent detection.
- **Plan** replaces "primary/fallback selection" as the output stage: a single-intent prompt produces a 1-step plan; a compound prompt produces an ordered multi-step plan. Fallbacks exist per step.
- **Confidence bands** replace binary "routable/non-routable": high/mid → route (with rationale), low → pass-through.

## 2. Discovery Contract (concrete, all four sources)

Deterministic rules: sorted traversal, stable fingerprints (mtime + size + content hash), **ignore cache directories** (`~/.claude/plugins/cache/`, `.git`, `node_modules`).

| Source | Location | Kind | Metadata source | Invocation syntax |
|---|---|---|---|---|
| Personal skills | `~/.claude/skills/**/SKILL.md` | skill | YAML frontmatter (name, description) + body | skill id / path |
| Project skills | `<workspace>/.claude/skills/**/SKILL.md` | skill | same | skill id / path |
| Personal agents | `~/.claude/agents/*.md` | agent | frontmatter (name, description, tools) | agent name |
| Project agents | `<workspace>/.claude/agents/*.md` | agent | same | agent name |
| Plugin skills | `~/.claude/plugins/<marketplace>/<plugin>/plugin-root/skills/**/SKILL.md` | plugin-skill | SKILL.md frontmatter + plugin manifest | plugin skill id |
| Plugin agents | `~/.claude/plugins/<marketplace>/<plugin>/plugin-root/agents/*.md` | plugin-agent | frontmatter + plugin manifest | plugin agent name |
| MCP servers (project) | `<workspace>/.mcp.json` → `mcpServers` | mcp-server | server name, command/env, tool names | server-scoped tool call |
| MCP servers (user) | `~/.claude.json` → `mcpServers` | mcp-server | same | server-scoped tool call |

**Capability index entry (union schema):**

``` ts
interface CapabilityIndexEntry {
  id: string;            // kind:sourcePath hash — stable
  kind: "skill" | "agent" | "plugin-skill" | "plugin-agent" | "mcp-server" | "mcp-tool";
  name: string;
  purpose: string;       // short "what it does for you"
  description: string;   // full description
  actions: string[];     // supported actions (verbs)
  domains: string[];     // domains/topics
  examples: string[];    // example triggers
  category: string;
  invocation: string;    // EXACT syntax the model emits to trigger it (new, required)
  sourcePath: string;
  fingerprint: string;
  enabled: boolean;      // from config
  weight: number;        // per-capability boost from config
}
```

Note on MCP: index **server-level entries plus their tools** (name + one-line description), compact. Fingerprints on the config file so `~/.claude.json` changes trigger a clean re-index of that server.

## 3. Deterministic Routing Core

### 3.1 Normalization
- lowercase → tokenize → **synonym/alias expansion** (config file; includes cross-language pairs, e.g. en↔hi, en↔zh, domain jargon) → stemming-lite (prefix/plural folding only, no heavyweight NLP).

### 3.2 Scoring → confidence
- Weighted field overlap: purpose ×0.35, actions ×0.25, domains ×0.20, examples ×0.10, description ×0.10.
- Score normalized to **confidence ∈ [0,1]** (overlap / max possible overlap).
- Tie-break: score desc → alphabetical (unchanged).

### 3.3 Confidence bands
| Band | Condition | Action |
|---|---|---|
| Route | confidence ≥ τ_route (default 0.55, configurable) | route; enhance with rationale + alternatives |
| Pass-through | confidence < τ_route | **safe pass-through** (no routing, no enhancement) |

τ_route is the single most important tuning knob for the 99% target — tuned by the eval harness, not by hand.

### 3.4 Determinism invariant
Same prompt + same index + same config → byte-identical decision. No randomness, no wall-clock dependence.

## 4. Multi-Capability Workflow Planning (new core feature)

### 4.1 Compound-intent detection (deterministic)
A prompt is compound when **any two** hold:
- connector patterns present: "then / and / also / after / first…then / 然后 / 并且 / 之后 / 再"
- ≥2 verb-object clusters separated by connectors
- ≥2 distinct domain peaks in scoring (top scores spread across unrelated domains)

### 4.2 Plan construction
``` ts
interface PlanStep {
  step: number;
  intent: string;              // deterministic restatement of this sub-intent
  primary: CapabilityIndexEntry | null;   // null → this step passes through
  fallbacks: CapabilityIndexEntry[];      // pre-ranked, no rescoring
}
interface ExecutionRequest {
  originalPrompt: string;      // byte-identical, always
  routed: boolean;
  plan: PlanStep[];
  enhancedPrompt?: string;     // present only if routed
  rationale?: string;          // one-line human-readable justification
}
```

- Single-intent prompt → 1-step plan (backward compatible with v1 semantics).
- Each step routed independently against τ_route; a step below threshold **passes through within the plan** (the plan continues for routed steps; if no step routes → full pass-through).
- Fallback chain per step: `primary → fallback[0] → fallback[1]`. Selection does not rescore (kept from v1).

### 4.3 Example
> "extract the tables from this PDF, then draft a summary email to the team"

→ Plan: `[ {intent: "extract tables from PDF", primary: skill:pdf-extractor, fallbacks: [mcp:pdf-tool]}, {intent: "draft summary email", primary: plugin-skill:gmail-draft, fallbacks: []} ]`

## 5. Intent-Boosting Prompt Enhancement (deterministic)

The enhanced block is injected as **routing context, not user speech**:

``` xml
<capability-routing>
  <intent>One-line restatement of what you understood</intent>
  <constraints>Extracted explicit/implicit requirements</constraints>
  <plan>
    <step n="1"><capability>name</capability><invoke>exact invocation syntax</invoke><alternatives>Y, Z (one-line rationale each)</alternatives></step>
  </plan>
</capability-routing>
```

Rules:
- original prompt stays **verbatim** (acceptance: byte-comparison)
- intent restatement built from matched terms — deterministic template, no invented requirements
- token budget **200–400 max**; only fields that actually matched are included
- top-3 alternatives + one-line rationale per step (transparency kills overwhelm — this is the anti-overload UX)

## 6. Eval Harness — the 99% measuring stick

### 6.1 Corpus
100–200 of **your real prompts**, each labeled:

``` json
{
  "id": "P001",
  "prompt": "…",
  "expect": {
    "route": true,
    "plan": [ { "primary": "skill:pdf-extractor" }, { "primary": "plugin-skill:gmail-draft" } ],
    "passThrough": false
  }
}
```

### 6.2 Metric suite (aligned to decision #3)
| Metric | Definition | Target |
|---|---|---|
| Routing accuracy@1 | of labeled-routable prompts: routed AND primary correct (per step for plans) | ≥ 99% |
| False-positive rate | chat-labeled prompts that got routed | ≈ 0 (pass-through precision ≥ 99.9%) |
| False-negative rate | routable-labeled prompts that passed through | ≈ 0 (recall ≥ 99%) |
| Plan correctness | multi-step labels: step order + per-step primary correct | ≥ 99% |
| Prompt preservation | byte-identical original prompt in every request | 100% |

### 6.3 Gate
Every change to detector / normalization / scorer / planner / enhancer re-runs the corpus in CI. **Baseline first**: measure the v1 scorer against the corpus before tuning (expect <50% — that number is the "before").

## 7. Feedback Loop (P1 — schema designed now, no rework later)

Local, append-only, no daemon (invariants preserved):
- **Decision log** (`UserPromptSubmit` hook): prompt hash, decision, plan, per-step confidences
- **Usage log** (`ToolUse` / `SessionEnd` hooks): which capability was actually invoked; user override if they steered elsewhere
- Feeds (P1): recency + success ranking boost; detector false-negative discovery ("routed but never used" / "passed through but should have routed"); slow weight drift

Design the two log schemas in Phase 0 so P1 is a pure addition.

## 11. Risks & Honest Math

1. **99% accuracy@1 with deterministic scoring is achievable only because of the pass-through band.** Prompts the scorer can't decide confidently simply don't route — so corpus labels must reflect that (hard/ambiguous prompts get `passThrough: true` labels). If the corpus is full of hard cases, the target silently drops; curate labels deliberately.
2. **Cross-language matching depends entirely on the alias map.** English-only metadata scores poorly on non-English prompts. The alias map is a P0 artifact, not a nice-to-have.
3. **Detector false negatives are the worst failure** (product becomes invisible → uninstall). Detector is catalog-driven (verb + domain phrase catalog), regression-tested, and fed by the P1 usage log.
4. **MCP tool explosion**: server-level + compact tool entries only; fingerprints on config files.
5. **τ_route is the make-or-break knob**: too low → false positives (violates decision #3); too high → false negatives (invisible product). It gets tuned by the harness, never by hand.

## 13. Implementation Status (2026-08-11) — ALL PHASES IMPLEMENTED & TESTED

Implemented in `capability-manager/` (zero runtime dependencies; Node ≥ 20).

| Phase | Deliverable | Gate result |
|---|---|---|
| 0+1 | Discovery (4 sources) + incremental index + eval harness + golden corpus | discovery coverage 100%; ADD/MODIFY/DELETE/UNCHANGED tests pass |
| 2 | Normalization + confidence scoring + τ=0.50 (harness-tuned) | all single-step corpus cases pass; FPR=0 |
| 3 | Compound-intent planner + per-step fallbacks | full corpus: accuracy@1=100%, FPR=0%, FNR=0%, planCorrect=100% |
| 4 | Enhancer (`<capability-routing>` block, token-budgeted) + CLI (install/uninstall/explain/validate) | idempotent install; unrelated hooks preserved; preservation 100% |
| 5 | hook-wrapper.mjs (UserPromptSubmit) + decision/usage logs (JSONL) + integration tests | routed → `additionalContext`; chat → `{}`; wrapper never throws |

**Key implementation decisions (measured, not guessed):**
- Scorer: per-field `max(queryPrecision, fieldRecall)` + `0.85·weighted + 0.15·strongest-field` blend; weights `purpose .30, actions .20, domains .15, examples .15, description .10, name .10`; `τ=0.50` (harness sweep found no single τ below 0.55 worked for all cases — dilution from non-intent tokens is real, so the confidence blend + alias map + main-clause truncation do the heavy lifting).
- Guards that make the 99% definition hold: `MIN_ROUTE_TOKENS=2` (1-token queries never route → P010 stays pass-through), stopword/alias hygiene (alias direction: `canonical: [variants]`; single-char aliases like `x→twitter` survive), relative-clause truncation (`…that…` dropped → "create a new skill" routes).
- Planner collapse rule: segments resolving to ≤1 distinct primary collapse back to a single intent; a null step inside a multi-routed plan passes through within the plan.
- Installer writes `runtime/capability-router/package.json` with `type: module` — without it Node treats the copied `.js` runtime as CJS and the hook silently no-ops (this exact failure was caught by the integration test).

**How to run (from `capability-manager/`):**
```bash
npm test                 # 32 tests, all phases
node dist/eval/harness.js --routing   # corpus metrics
npm run install:cr       # registers the hook (idempotent)
npm run explain "<prompt>"            # scoring breakdown
npm run validate         # install integrity
```

**Remaining (per blueprint):** grow `eval/corpus.json` to 100–200 real prompts and re-tune τ/weights with the harness; wire the P1 usage-log hooks (ToolUse/SessionEnd — schema already frozen in `src/logs.ts`); real-machine install & hook validation on a Claude Code instance.
